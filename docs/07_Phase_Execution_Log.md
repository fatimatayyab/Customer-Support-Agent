# Phase Execution Log

**Purpose:** Track what was actually built, verified, and decided in each implementation phase — a running record of execution, not a design document. The other docs (00-06) remain the source of truth for architecture and requirements; this log records how and when that architecture was realized, and any decisions made during implementation that future phases need to know about.

---

## Phase 0 — Foundation

**Status:** ✅ Completed & Verified

### Key Deliverables Built

- Monorepo structure: pnpm workspaces across `apps/api` (Fastify), `apps/dashboard` (Next.js), `apps/widget` (Preact, compiled to a standalone Shadow-DOM-mounted IIFE bundle), `packages/db` (Drizzle), `packages/shared` (shared types).
- Drizzle ORM schemas for `workspaces`, `users`, `workspace_api_keys`, matching the Domain Model exactly (a User belongs to one Workspace).
- Dockerized local infrastructure: PostgreSQL with pgvector, Redis.
- Authentication: JWT session cookies for the dashboard, SHA-256-hashed API keys for the widget — both implemented as the System Architecture's "Workspace Identification" step.
- Widget embedding proven via a real `<script>` tag on a simulated third-party host page, mounting into a Shadow DOM root for CSS/JS isolation.

### Architectural Security Highlights

- **Dual-layer multi-tenancy.** An application-layer `withWorkspaceContext()` transaction wrapper is the only path to any tenant-owned table (no repository function accepts the raw, unscoped `db` client). PostgreSQL Row Level Security backs this as defense-in-depth, enforced against a dedicated non-superuser `app_user` role (migrations run as `postgres`, which owns the tables, so RLS applies to `app_user` without needing `FORCE ROW LEVEL SECURITY`).
- **Hyper-constrained `auth_resolver` role.** Resolving a public identifier (a widget API key, or a workspace slug at login) into a `workspace_id` has to happen *before* a request has tenant context — RLS can't cover that by construction. Rather than let the whole app bypass RLS, a single `auth_resolver` Postgres role exists for exactly this: `BYPASSRLS`, but granted `SELECT` on only 3-4 specific columns across two tables (`workspaces`, `workspace_api_keys`). The blast radius of the bypass is small and auditable.

### Infrastructure Notes

- **Port 5433, not 5432.** The dev machine already runs a native Postgres service bound to 5432; the Dockerized Postgres for this project is mapped to host port 5433 to avoid silently talking to the wrong database. All local connection strings (`.env`) reflect this.
- **Fastify plugin registration must not be awaited individually.** `fastify.register()` returns a thenable, and `await`-ing each call individually triggers an implicit `ready()`/boot at that point, which silently locks in whatever's registered so far and skips everything registered afterward (including `setErrorHandler`). `apps/api/src/app.ts` registers all plugins/routes synchronously (no `await`) and lets the real boot happen once, when `server.ts` calls `app.listen()`.
- **CORS is single-registration with a per-request delegate**, not two separate `@fastify/cors` registrations — the plugin installs one global wildcard `OPTIONS` route for preflight handling, which collides if registered twice on the same Fastify instance. `corsOptionsFor(request)` in `app.ts` branches on path prefix (`/widget/*` = open CORS, no credentials; everything else = locked to `DASHBOARD_ORIGIN`, credentials on).

## Phase 1 — Conversation & Messaging Infrastructure

**Status:** ✅ Completed & Verified

### Key Deliverables Built

- Drizzle schemas + RLS for `customers`, `conversations`, `messages`, wired through the same `withWorkspaceContext()` pattern as every Phase 0 table.
- `SupportOrchestrator` (`apps/api/src/orchestrator/support-orchestrator.ts`) — the literal System Architecture component, implemented as plain functions (`initiateConversation`, `handleCustomerMessage`) rather than a class, matching the rest of the codebase's style. This is the seat Phase 3 (AI calls, including wiring in Phase 2's Knowledge retrieval), Phase 4 (escalation), and Phase 5 (Integration actions) all extend rather than replace.
- Real-time transport: `@fastify/websocket` at `GET /widget/ws`, fronted by a ticket-exchange handshake (`POST /widget/session`) to work around browsers not allowing custom headers on a WS upgrade.
- In-process conversation hub (`Map<conversationId, Set<WebSocket>>`) for message/typing fan-out — deliberately not Redis-backed yet (see below).
- Widget chat UI (Preact): bubble → panel toggle, message history, live send/receive, ephemeral typing indicator, all inside the existing Shadow DOM mount.

### Decisions Made During Implementation

- **Conversation status enum:** used the full lifecycle from `04_Domain_Model.md` (`open, waiting_for_customer, escalated, assigned, resolved, closed`) instead of the shorthand 3-value version floated at kickoff, to avoid a guaranteed rename when Phase 4 needs the finer-grained states. Confirmed with the user before implementing.
- **Added a minimal `customers` table** (`id`, `workspace_id`, `created_at` only) that wasn't in the original Phase 1 schema list but is required by `conversations.customer_id` per the Domain Model. Customers are anonymous in Phase 1 — no name/email/tags until a pre-chat form or CRM integration exists. Identity is a client-generated id the widget persists to `localStorage` on the *host page's* origin, which is what makes multi-tab sync within one customer's browser work for free.
- **WebSocket auth via short-lived ticket, not a raw API key in the URL.** `POST /widget/session` (authenticated via the existing `requireApiKey`) issues a 60-second single-purpose JWT; the widget opens `GET /widget/ws?ticket=...` with that instead of the long-lived key, avoiding a durable credential in a URL that proxies/browser history/logs would otherwise capture.
- **`conversation:initiate` treats a resumed `conversationId` as authoritative** over any separately supplied `customerId` — if the conversation resolves, its own `customerId` wins; a stale/invalid `conversationId` falls back to resolving-or-creating the customer and starting fresh. Never trusts client-supplied ids without a workspace-scoped DB lookup first.
- **No AI or canned auto-replies.** This phase is transport and persistence only; `message:receive` only fires for real, authored messages (customer messages today, agent/AI in later phases).
- **Real-time fan-out is in-process, not Redis-backed**, on the same reasoning as Phase 0's Redis notes — one API instance, no infra to run more yet. `publishToConversation`/`subscribe`/`unsubscribe` in `conversation-hub.ts` are the only surface callers use, so swapping in Redis pub/sub later shouldn't require changes outside that file.
- **Deferred, not built:** `attachments`/`ai_metadata` on messages, `sender_user_id` for agent messages. Nullable columns, cheap to add exactly when Phase 3 (AI) or Phase 4 (Agent Console) needs them.

### Verified

- CLI WebSocket smoke test: ticket issuance → connect → `conversation:initiate` → `message:send` → `message:receive` round trip, confirmed against the real API and database.
- Browser verification via Playwright: two tabs on the same simulated host-page origin, sharing `localStorage`, both connect to the *same* conversation; a message sent from either tab appears live in both; typing in one tab shows the indicator in the other. Zero console errors, zero failed requests.

## Phase 2 — Knowledge & RAG

**Status:** ✅ Completed & Verified

### Key Deliverables Built

- Drizzle schemas + RLS for `knowledge_sources` and `knowledge_chunks`, following the same `withWorkspaceContext()` pattern as every prior table.
- A `vector` column type (`packages/db/src/schema/vector-type.ts`) via Drizzle's `customType` — this version of Drizzle has no first-class pgvector support — plus an HNSW index with `vector_cosine_ops` on `knowledge_chunks.embedding`.
- `EmbeddingProvider` interface (`apps/api/src/modules/knowledge/embedding-provider.ts`) with a `VoyageEmbeddingProvider` implementation (`voyage-3-lite`, 512 dimensions) — mirrors the PRS's "AI provider-independent" stance for the generation layer, applied to embeddings.
- A simple paragraph-aware chunker (target size + overlap, character-based, no tokenizer dependency).
- `knowledge.service.ts`: ingestion (`createKnowledgeSource`) and retrieval (`searchKnowledge`), both dashboard-facing (session-authenticated) — **not** wired into the live widget chat yet. That combination (retrieval + generation) is Phase 3's job.
- Dashboard Knowledge page: add a plain-text/FAQ source, see status update live via polling, run a search and see ranked results with similarity scores.

### Decisions Made During Implementation

- **Embedding provider: Voyage AI (`voyage-3-lite`, 512 dims)**, confirmed with the user before implementing — Anthropic has no embeddings API of its own and explicitly recommends Voyage for RAG use cases, keeping the AI stack aligned with the Claude-first strategy in `00_Product_Requirement_Specification.md` rather than adding an unrelated second vendor (e.g. OpenAI) for embeddings alone.
- **Ingestion scope: `plain_text` and `faq` only.** `pdf`, `docx`, `website` exist in the `knowledge_source_type` enum (per `04_Domain_Model.md`) so the schema won't need to change later, but the service rejects them for now (`UnsupportedSourceTypeError`) rather than pretending to support them. Matches the original Phase 2 scoping (start with text, defer file parsing and crawling).
- **Processing is in-process background work, not a blocking request or a real job queue.** `createKnowledgeSource` returns immediately after inserting the source row (`status: pending`); chunking + embedding happen in an un-awaited call, updating status to `processing` → `completed`/`failed`. The dashboard polls for status. Tradeoff: an API restart mid-processing leaves a source stuck in `processing` until manually retried — acceptable for small text sources today; a real queue with retries becomes worth the complexity once pdf/website ingestion makes this slower or higher-volume.
- **Retrieval is a standalone, dashboard-testable capability, not wired into the chat yet.** `SupportOrchestrator` was deliberately not touched this phase — combining retrieval with generation is Phase 3's responsibility, and wiring it in early would mean building it twice.
- **`EmbeddingProviderNotConfiguredError` is a proper `AppError` (503),** not a generic thrown `Error` — knowledge routes are dashboard/admin-only (not customer-facing), so surfacing "set VOYAGE_API_KEY" directly is more useful than collapsing it to a generic 500.

### Verified

- Real end-to-end run against the live Voyage API (once the user provided a key): created two topically distinct sources (Refund Policy, Shipping FAQ), both reached `completed`, and cross-queried each — "does express shipping cost extra?" ranked Shipping FAQ first (0.541 similarity) over Refund Policy (0.250); "can I get my money back?" ranked Refund Policy first (0.386) over Shipping FAQ (0.132). Confirms the embeddings are actually semantically discriminative, not just returning whatever exists.
- Tenant isolation re-confirmed on the new tables: Beta Co's `/knowledge/sources` and `/knowledge/search` both return empty against Acme's data.
- Dashboard Knowledge page browser-verified via Playwright: added a third source through the UI, watched it move from `pending` through the polling loop to `completed`, then searched and got the correct top result with its similarity score displayed. Zero console errors, zero failed requests.

### Pre-Commit Architecture Review

Before committing, a final review against long-term maintainability, scalability, security, tenant isolation, performance, extensibility, and Engineering Bible/System Architecture consistency surfaced three issues worth fixing immediately (project still small, all cheap to fix now):

1. **Missing `workspace_id` indexes.** A direct catalog check found `conversations`, `messages`, `customers`, `knowledge_sources`, `knowledge_chunks`, and `workspace_api_keys` had no index touching `workspace_id` at all beyond the primary key - every RLS policy and most app queries filter on it. Fixed by adding a plain `workspace_id` index to each, plus composite indexes matching the actual query shapes already in the code (`knowledge_sources`: `(workspace_id, created_at)`; `messages`: `(conversation_id, created_at)`). This was a pre-existing gap since Phase 0/1, not new to Phase 2, but Phase 2 added two more affected tables and was the natural point to close it everywhere in one pass.
2. **No role check on `/knowledge/*` mutation routes.** `workspace.routes.ts` established the pattern (API key management gated to `owner`/`administrator`); `knowledge.routes.ts` didn't follow it, meaning any authenticated role including `support_agent` could create/delete knowledge sources. Fixed by extracting the previously-duplicated inline guard into a shared `requireRole()` helper (`apps/api/src/modules/auth/require-role.ts`), used by both `workspace.routes.ts` (refactored) and the new `knowledge.routes.ts` guards on create/delete. Search stays open to all authenticated roles - it's read-only, and agents may want it to help customers. Verified directly: a temporary `support_agent` test account got a 403 on create, a 200 on search; the existing `owner` flow regression-checked clean.
3. **No batching against the embedding provider's request limits.** The dashboard's own `content` field allows up to 200,000 characters, which can chunk into ~250 texts sent in one Voyage API call - reachable today via a single long paste, not just a hypothetical future PDF. Fixed by splitting `embed()` into sequential sub-batches (`MAX_BATCH_SIZE = 100`) in `voyage-embedding-provider.ts`. Sequential rather than parallel batches deliberately, to avoid bursting concurrent requests (and cost) at the provider for one large document.

One issue was surfaced but deliberately left as a documented note rather than fixed: pgvector's HNSW index doesn't natively combine with a `WHERE workspace_id` filter the way a btree index would (Postgres applies the filter to the ANN candidate set, not the index scan itself) - at real scale, a workspace with few chunks could get fewer than `limit` results if other workspaces' chunks dominate the nearest-neighbor candidates. Not an issue at today's per-workspace chunk counts; noted in `knowledge-chunks.ts` for whoever revisits it once that's a real concern.

All fixes re-verified end-to-end after the changes (migration applied, role guard tested against both an allowed and blocked role, batching confirmed not to break normal small-document processing) before being considered ready to commit.

## Phase 3 — AI Service

**Status:** ✅ Completed & Verified

### Key Deliverables Built

- `apps/api/src/modules/ai/` — the AI Service the System Architecture names, wired into the Support Orchestrator for the first time (Phase 2 deliberately left this combination undone). Structure:
  - `ai-provider.ts` — the `AiProvider` interface and every provider-neutral type (`GenerateReplyInput`, `AiReplyResult`, `Citation`, `AiUsage`).
  - `ai.config.ts` — named tuning constants (`CONFIDENCE_ESCALATION_THRESHOLD`, `MIN_RELEVANCE_SIMILARITY`, `MAX_HISTORY_MESSAGES`, `RETRIEVAL_LIMIT`, `MAX_OUTPUT_TOKENS`), since there's no per-workspace `AI Configuration` entity yet.
  - `prompts/support-reply.prompt.ts` + `prompts/fallback-messages.ts` — system/user prompt text and the structured-output schema live here, not inside a provider file.
  - `providers/anthropic-ai-provider.ts` and `providers/gemini-ai-provider.ts` — two working implementations of `AiProvider`, selected at startup by `AI_PROVIDER=anthropic|gemini` (`ai.service.ts`'s `createAiProvider()`). Nothing outside `ai.service.ts` imports either provider class directly, including the Orchestrator.
- `support-orchestrator.ts`: `handleCustomerMessage` now kicks off an un-awaited `generateAiReply()` after persisting the customer's message (same fire-and-forget shape as Phase 2's knowledge processing) — retrieval → generation → persist → broadcast, with a server-sent `typing:start`/`typing:stop` around it (reusing Phase 1's existing wire event, zero new protocol, zero widget code changes needed).
- `messages.metadata` (nullable jsonb) — the column Phase 1's decision log flagged as "cheap to add exactly when Phase 3 needs it." Populated only for `ai`-sender messages: `{ provider, model, promptVersion, confidence, citations, usage, finishReason }`.
- `conversations.escalateConversation()` — merges `{ escalation: { reason, detail, escalatedAt } }` into the existing `conversations.metadata` (jsonb `||`, not an overwrite) and sets `status = 'escalated'`, the enum value that's existed unused since Phase 1. `EscalationReason` is a closed union (`no_relevant_knowledge`, `low_confidence`, `ai_requested_escalation`, `ai_provider_error`) so a future Agent Console can distinguish these instead of parsing free text.

### Decisions Made During Implementation

- **Provider-agnostic by explicit instruction, not just interface hygiene.** The user asked specifically not to depend on a paid API during active development: `AI_PROVIDER` defaults to `gemini` (free tier), with `anthropic` fully implemented and selectable via one env var, not a stub. Adding a third provider is one new file under `providers/` plus one new `switch` case in `ai.service.ts` — nothing in the Orchestrator, prompts, or config changes.
- **Structured output via forced tool/function-calling, not prompted JSON-in-prose.** Both providers force a single tool call (`respond_to_customer`) so parsing is deterministic. The schema itself (field names, types, descriptions, required list) is one plain, provider-neutral JSON Schema object in `support-reply.prompt.ts` — Anthropic's SDK consumes it as `Tool.input_schema` and Gemini's as `FunctionDeclaration.parametersJsonSchema` with zero transformation, since `@google/genai` accepts standard JSON Schema directly. This is what makes "add a third provider with minimal changes" actually true rather than aspirational.
- **`AiReplyResult.provider` is set by each provider itself, not assumed by the caller.** Caught in testing: an early version had the Orchestrator hardcode `provider: "anthropic"` into message metadata regardless of which provider actually ran. Fixed by making `provider` part of the neutral result type — exactly the kind of leak the "no provider-specific code in the Orchestrator" instruction was meant to prevent, and a good example of why that constraint needed a code fix, not just an interface that looked clean.
- **Two independent, structural guarantees against answering from general knowledge** (the user's explicit fifth requirement), not just a prompt instruction: (1) knowledge chunks below `MIN_RELEVANCE_SIMILARITY` (0.25, informed by Phase 2's real measured scores) are filtered out before the AI ever sees them, and if *nothing* clears that floor, the provider is never called at all — a structural guarantee, not a hope that the model complies; (2) the system prompt separately instructs the model to refuse rather than guess even when it is called with weak-but-present context. Confidence/escalation sits on top as a third, independent layer.
- **A low-confidence or self-escalating reply is still shown to the customer, not suppressed.** Only two cases get a fully hardcoded fallback message instead of the model's own words: zero relevant chunks retrieved (never calls the model), and a provider-level failure (bad/missing key, network error, or the model not returning a usable function call at all). If the model *did* answer using only the provided context but flagged low confidence or requested escalation itself, its actual reply is honest and grounded — showing it is more useful than replacing it with a canned message, and the conversation still flips to `escalated` either way.
- **Gemini's model id is a floating alias (`gemini-flash-latest`), not a dated pin like Anthropic's.** A dated model tried during implementation (`gemini-2.5-flash`) was rejected outright ("no longer available to new users") despite still appearing in the models-list endpoint — new API keys and dated model snapshots don't mix reliably on this provider. Since Gemini is specifically the low-stakes, cost-free dev-iteration path here (not the reproducibility-sensitive one), a floating alias is the right tradeoff; the concrete resolved model still gets recorded per-message via `response.modelVersion`, so there's an audit trail regardless.
- **`PROMPT_VERSION` (`prompts/support-reply.prompt.ts`) travels through `AiReplyResult` into `messages.metadata` the same way `provider` does** — each provider reports it, not the Orchestrator, even though both providers currently import the identical prompt file. Bump it whenever the prompt wording or schema changes meaningfully; it's what lets a later quality comparison ("did replies get better after that wording change?") key off which prompt version actually produced each stored reply. Exact model name was already correctly captured before this request (verified against both SDKs' response types, not just assumed) — `promptVersion` was the genuinely missing field.

### Verified

- Real end-to-end run against the live Gemini free tier: grounded questions ("What is your refund policy?", "What time are you open?") returned correct, cited answers (confidence 1.0, correct source chunk cited) with `metadata.provider` correctly recorded as `"gemini"`.
- No-relevant-knowledge path: an off-topic question never reached the provider at all and produced the hardcoded fallback + `escalated` status with reason `no_relevant_knowledge`.
- AI-requested-escalation path: an account-specific, frustrated-customer message ("refund my order #48213 RIGHT NOW") produced an honest, grounded, empathetic reply *and* flipped the conversation to `escalated` with reason `ai_requested_escalation` — confirmed the model's own reply is preserved rather than replaced.
- Provider-failure path: reproduced twice — once via a genuinely invalid model id, once via Gemini occasionally not honoring forced function-calling for a given generation (confirmed non-deterministic by re-running the identical input, which then succeeded) — both times failed safely to the hardcoded fallback + `ai_provider_error` escalation, no crash, no hallucinated answer shown.
- Tenant isolation re-confirmed on the new code path specifically (not just the tables): a cross-workspace check that AI generation for one workspace only ever retrieves and cites that workspace's own knowledge chunks.
- Browser-verified via Playwright: asked a question through the actual widget UI, confirmed the AI's reply rendered correctly using Phase 1's pre-existing `.message-ai` styling and the typing indicator fired during generation — zero widget code changes required, confirming the wire-protocol reuse worked as designed. Zero console errors, zero failed requests.

## Phase 4 — Collaborate (Human Handoff & Agent Console)

**Status:** ✅ Completed & Verified

### Key Deliverables Built

- **Schema:** `conversations.assignedUserId` (nullable FK → `users.id`, `ON DELETE SET NULL`) plus two composite indexes (`workspace_id, status` and `workspace_id, assigned_user_id`); `messages.senderUserId` (same nullable/`SET NULL` pattern) so an agent-sent message records who sent it. New `conversation_notes` table — a separate table rather than a new `messages.sender_type` value, workspace-scoped, RLS-enabled, indexed on `(workspace_id)` and `(conversation_id, created_at)`.
- **AI Service extension:** `summarize()` added to the `AiProvider` interface and implemented by both `AnthropicAiProvider` and `GeminiAiProvider`; `prompts/summarize-conversation.prompt.ts` (`SUMMARIZE_PROMPT_VERSION = 1`) follows the same "prompt lives outside the provider file" pattern Phase 3 established. `ai.service.ts` exports `summarizeConversationHistory()`.
- **Support Orchestrator additions:** `claimConversation`, `changeConversationStatus`, `sendAgentMessage`, `addInternalNote` (never broadcasts), `suggestReplyForAgent` (returns a draft, never persists or broadcasts), `summarizeConversationForAgent`. `handleCustomerMessage` now returns `assignedUserId` from its transaction and only kicks off the fire-and-forget AI reply `if (!assignedUserId)` — this single gate is the entire "live takeover" mechanism.
- **Routes:** `modules/conversations/conversation.routes.ts` (session-cookie authenticated, no role restriction — handling conversations is core `support_agent` work per the Domain Model) exposes list/detail/claim/messages/notes/suggest-reply/summarize/status. `modules/realtime/agent-console-ws.routes.ts` authenticates the dashboard's WebSocket via the same session cookie the browser already sends automatically on the handshake — no ticket exchange needed (that pattern stays reserved for the widget, which has no cookie to rely on).
- **Dashboard UI:** `/conversations` (queue, Unassigned/Mine/All tabs, 5s poll) and `/conversations/[id]` (message history over a live WS connection, claim/reassign button, status dropdown, AI summary panel with regenerate, suggested-reply-into-draft, internal notes sidebar).

### Decisions Made During Implementation

- **Internal notes live in their own table, not a new `messages.sender_type`.** Presented as an explicit choice via `AskUserQuestion`; the separate-table option was selected. Reusing `messages` would require every current and future query/broadcast path to remember to filter notes out — one missed filter is a customer-facing information leak. A separate table makes that leakage structurally impossible: the widget-facing code never queries `conversation_notes` at all. Verified live (see below), not just by inspection.
- **Claim/reassign UX is a state-aware client-side affordance, backend stays permissive.** Per explicit user instruction. The detail page shows "Claim" when unassigned, nothing (+"Assigned to you") when it's already yours, and "Reassign to me" — gated by a `window.confirm()` — when it's someone else's. The backend does not enforce any of this; any session-authenticated agent can call `POST /claim` regardless of current assignment. Every claim/reassign posts an automatic `system`-sender audit message ("X claimed this conversation." / "Reassigned from X to Y.") through the existing message/broadcast infrastructure — both a permanent record and a live notification to anyone watching, with zero new event types.
- **Read-vs-write split follows existing precedent, not a new rule.** `GET /conversations` and `GET /conversations/:id` call the repository directly from the route (matching `workspace.routes.ts` / `knowledge.routes.ts`), since a single-module read isn't cross-module orchestration. Every state-changing or AI-invoking action goes through the Orchestrator.
- **`PATCH /conversations/:id/status` deliberately accepts a narrower enum (`open | resolved | closed`) than the full six-value lifecycle.** `assigned` only ever happens via `claimConversation`, `escalated` only via the AI's own escalation path (Phase 3) — this endpoint is for the explicit human actions of resolving, closing, or reopening, not for hand-setting every internal state.
- **Assignee/sender/author display names are resolved via direct SQL joins against `users`** (`conversationWithAssigneeColumns`, `listMessages`'s `leftJoin`, `listConversationNotes`'s `innerJoin`) rather than standing up a separate user-listing endpoint — no second use case yet to justify that abstraction.

### Bugs Found and Fixed During Verification

- **`apps/dashboard/lib/api.ts`'s `apiFetch` unconditionally set `Content-Type: application/json`, even on bodyless POSTs.** Fastify rejects an empty body sent with that content-type (`FST_ERR_CTP_EMPTY_JSON_BODY`), which surfaced as a 500 on Claim, Suggest, and Regenerate-summary — all three are bodyless POSTs, all three worked fine via `curl` (which doesn't set the header without `-d`) and only broke through the real browser UI. This is exactly the class of bug §17 exists to catch — typecheck and curl both looked clean. Fixed by only attaching `Content-Type` when `init.body` is present.
- **`error-handler.ts` collapsed every non-`AppError`/`ZodError` exception to a generic 500,** discarding a framework-level `FastifyError`'s own accurate status code (the empty-body case above is a legitimate 400, not a 500). Added a pass-through branch for any error carrying its own 4xx `statusCode` before falling through to the generic 500/log branch — a defense-in-depth fix independent of the client-side one above, since any caller sending a malformed request should get an honest 4xx.
- **The status `<select>` bound `value={conversation.status}` but only listed `open`/`resolved`/`closed` as `<option>`s.** When the real status was `assigned` (or would be `escalated`/`waiting_for_customer`), the browser silently fell back to displaying "Open" — the first option — misrepresenting an assigned conversation as unclaimed. Fixed by rendering a disabled `<option>` for the current status when it falls outside the three manually-settable values, so the dropdown always displays the true state while still only allowing the three real transitions.

### Found in Pre-Commit Review (post-verification, before first commit)

A second pass — re-reading the diff fresh, checked against architectural consistency, security, tenant isolation, scalability, DB design, WS correctness, API design, and edge cases — caught four more issues the runtime verification above didn't exercise:

- **The `error-handler.ts` FastifyError pass-through (added during the bug-fix pass above) was duck-typed too loosely.** It matched any thrown object with a numeric 4xx `statusCode`, not just genuine Fastify framework errors. Confirmed concretely exploitable, not just theoretical: `@google/genai`'s `ApiError` type carries exactly that shape, so a Gemini failure during `suggest-reply` or `summarize` (bad key, quota, rate limit) would propagate through this branch and leak the raw provider error message to the dashboard client — defeating the file's own stated purpose ("the only place that decides what's safe to expose"). Fixed by additionally requiring `error.code` to start with `FST_`, so only Fastify's own framework errors (documented as client-safe) pass through.
- **`summarizeConversationForAgent` sent the entire, unbounded message history to the AI provider**, unlike `generateAiReply`/`suggestReplyForAgent`, which both cap context with `MAX_HISTORY_MESSAGES`. Contradicted the established "don't send an unbounded batch to a paid external API" guardrail and was user-triggerable repeatedly via "Regenerate summary" on arbitrarily long threads. Fixed with the same `.slice(-MAX_HISTORY_MESSAGES)`.
- **`saveConversationSummary` silently dropped `promptVersion` and `usage`** even though `SummarizeResult` carries both and every provider populates them — a regression against the precedent Phase 3 deliberately set (provider/model/promptVersion recorded on every AI-generated artifact). Fixed by extending the repository function's parameter type to include both; the JSON-merge already spread the whole object, so no separate persistence-path change was needed.
- **Missing index for the "All" conversations tab's actual query shape.** `listConversations` with no filter still does `ORDER BY updated_at DESC`, but none of the three existing indexes (`workspace_id` alone, `+status`, `+assigned_user_id`) supports that sort — the exact class of gap CLAUDE.md §8 already calls out as previously missed "for two phases before a review caught it." Added `conversations_workspace_id_updated_at_idx` (migration `0007_lyrical_chimera.sql`).

Not flagged as issues (checked and confirmed pre-existing/consistent, not Phase-4 regressions): no WS reconnect/disconnect indicator on the agent console — the widget's Phase-1 `ChatConnection` has the identical gap, so Phase 4 mirrored existing precedent rather than introducing a new one; no pagination on `listConversations` — consistent with every other list endpoint in the codebase today.

## Phase 5 — Integration Service ("Act")

**Status:** ✅ Completed & Verified (first provider/action only — see scope notes below)

### Key Deliverables Built

- **Schema:** `integrations` (per-workspace connection: `provider` enum, non-secret `config` jsonb, encrypted `credentials`, `status`, `last_verified_at`, unique on `(workspace_id, provider)`) and `integration_action_logs` (the audit trail `02_Product_Blueprint.md`'s Act pillar requires — `action_name` as free text rather than an enum, since there's no approved upfront list the way `conversation_status` had one; `integration_id` nullable with `ON DELETE SET NULL`, not cascade, so disconnecting an integration can't erase its own audit history). Both RLS-enabled, workspace_id-indexed, migrations `0008_jittery_gorilla_man.sql` / `0009_shiny_leper_queen.sql` (the second fixing the cascade-vs-set-null decision after live testing caught it — see below).
- **`apps/api/src/modules/integrations/`:** `integration-provider.ts` (the `IntegrationProvider` interface, mirroring `AiProvider`/`EmbeddingProvider`), `providers/hubspot-integration-provider.ts` (the only implementation — Private App access token, HubSpot CRM v3 API), `credential-crypto.ts` (encryption at rest via `jose`'s JWE, not hand-rolled `crypto` calls — a new `INTEGRATION_CREDENTIALS_KEY` env var), `integration.repository.ts`, `integration-action-log.repository.ts`, `integration.service.ts` (the workspace-aware entry point — per-workspace data, not an env-var-selected singleton like `ai.service.ts`), `integration.routes.ts`.
- **Orchestrator addition:** `lookupContact(workspaceId, conversationId, userId, email)` — the only new function this phase needed. Logs every attempt to `integration_action_logs` regardless of outcome; a successful result is written to `conversation_notes` (agent-only), never broadcast as a `messages`-table system message, since a CRM record isn't the same safe-to-show-the-customer category as a claim/reassign audit line.
- **Route addition:** `POST /conversations/:id/actions/contact-lookup` — a specific name, not a generic `/actions/:actionName` dispatcher, matching how there's exactly one action to date.
- **Dashboard:** `/integrations` settings page (owner/admin only, matches API-key/knowledge-base management precedent) and a "Check contact" action in the conversation console, rendered only when a HubSpot integration is connected.

### Scope, deliberately narrow (see the design discussion earlier in this session for the full reasoning)

- **One provider (HubSpot), one action (`lookupContact`), agent-triggered only — the AI never calls this itself.** All three were explicit decisions, not defaults assumed without asking.
- HubSpot was reconsidered mid-design: an initial Shopify pick (docs' own "check an order" example) was replaced with HubSpot specifically because a CRM contact-lookup generalizes across every vertical this platform targets (textile, healthcare, education, logistics, restaurants, travel), where "order status" is e-commerce-specific.
- A proposal to make the *first* provider a generic, configurable REST connector was evaluated and rejected: it would mean designing a full auth-scheme-agnostic request/response mapping engine with zero real integrations to validate the design against — the "wait for the second use before generalizing" principle (CLAUDE.md §16) applied to an even more extreme case (guessing before even a *first* concrete case exists). The interface layer is already appropriately generic (`lookupContact`, not `getHubSpotContact`); only the implementation stayed concrete, which is where genericity belongs at this stage.
- Auth is a static Private App access token, not OAuth2 authorization-code flow — no redirect/callback route, no refresh-token rotation. OAuth2 only becomes necessary for a HubSpot-Marketplace-listed "Connect with HubSpot" experience, a materially bigger scope deferred until there's a real reason to build it.

### Decisions Made During Implementation

- **Interface named for the business capability, not the vendor** (`lookupContact`, not `getHubSpotContact`) — the same discipline `AiProvider.generateReply()`/`summarize()` already follow, applied here explicitly rather than drifting into vendor-flavored naming. `ContactLookupResult` is a genuinely neutral field set (`name`, `email`, `phone`, `company`, `lifecycleStage`, plus `sourceProvider`/`sourceRecordId` set by the provider itself) — not a passthrough of HubSpot's raw property names, which would have leaked the vendor into the contract even with a well-named method. "Contact" (not "Customer") was chosen deliberately to avoid colliding with this codebase's existing `Customer` entity (the anonymous widget visitor) — a completely different concept from a business's own CRM record.
- **Vendor knowledge kept to exactly two places: the provider implementation and the audit trail.** The Orchestrator and route are vendor-neutral (`lookupContact`, `/actions/contact-lookup`); `integration.service.ts` is the one place that knows it's dispatching to HubSpot specifically; `integration_action_logs` links to `integrations.provider` so the audit trail stays concrete even though the interface stays neutral — the same split `messages.metadata.provider` already uses for AI replies (neutral call, concrete record).
- **Credential encryption via `jose`'s JWE, not hand-rolled AES/`crypto` calls.** `jose` is already a trusted dependency for exactly this class of problem (session JWTs) — reusing it for encryption-at-rest avoided hand-writing IV/tag/key-management bookkeeping for a stored secret that (unlike a password or API key) has to be decrypted back to plaintext to actually call the provider.
- **Action results go to `conversation_notes`, never a broadcast `messages` system message** — this was flagged as an easy mistake to make (claim/reassign audit lines *do* broadcast to the customer, and reusing that pattern was the first instinct) and deliberately corrected before building: a CRM lookup result is a different category of content an agent may not have vetted for customer visibility yet.

### Bugs Found and Fixed During Live Verification

- **A bad HubSpot token surfaced as a generic 500** (`connectHubspot`'s verify-before-save step threw a plain `Error`, not an `AppError`, so it fell through to the error-handler's generic branch) instead of a clear, actionable message. Fixed by catching and rethrowing as an `AppError` (400) — safe to be specific since this route is dashboard-only, never customer-facing.
- **Credential decryption failures bypassed the audit log entirely.** `lookupContact`'s try/catch only wrapped the provider's HTTP call, not the `decryptCredentials` step before it — a corrupted or unreadable stored credential (e.g. after a future key rotation with no migration) would throw past the catch block, skip the `integration_action_logs` insert, and surface as an unhandled 500. Widened the try/catch to cover decryption too, confirmed via a deliberately corrupted test row: now logs a clean `failure` entry and returns a proper 502.
- **`integration_action_logs.integration_id` cascaded on delete**, meaning disconnecting an integration silently destroyed the audit history of everything ever done through it — backwards for a table whose entire purpose is surviving the thing it's about. Changed to nullable + `ON DELETE SET NULL` (migration `0009_shiny_leper_queen.sql`), the same pattern `messages.senderUserId` already uses to survive a deleted user account. Caught by actually testing the delete path against a real row, not just reading the schema back.

### Verified

- Structural correctness confirmed against HubSpot's real API (not a mock): a fake access token produced a genuine `401` from `api.hubapi.com`, proving the request URL, auth header, and endpoint shape are correct — full success-path verification (a real contact record returned and rendered) needs a real HubSpot Private App token, which wasn't available this session.
- Credential encryption round-trip: encrypting a token produces a JWE string that does not contain the plaintext substring anywhere in it, and decrypting it recovers the exact original value.
- Tenant isolation cross-check on both new tables: a Beta Co session's `GET /integrations` returned empty against an Acme-workspace row inserted directly, and Beta Co's `DELETE` against that row's id returned 404 without affecting it.
- Audit logging verified for both outcomes: a failed lookup (corrupted test credentials) produced a `failure`-status row with the real error message; the fix above confirmed the same row survives with `integration_id` set to `null` after the referenced integration is deleted, rather than disappearing.
- Confirmed a failed lookup does **not** produce an internal note (only a successful, found result does) — no stray note appeared after the failure-path tests.
- Browser-verified via Playwright: the bad-token connect error renders correctly in the `/integrations` UI; the conversation console's "Check contact" section only appears when an integration is connected, and a lookup attempt's error surfaces inline without crashing the page. Zero unexpected console errors (the 400/502s were the deliberate test cases themselves).
- All test rows (fake integrations, action logs) removed after verification — nothing left behind in the database.

## Milestone: Design-Partner Readiness — Team Management (Invitations)

**Status:** ✅ Completed & Verified

Deliberately not "Phase 6." Following a strategic review after Phase 5, work shifted from the phase-numbered roadmap (Learn/Understand/Answer/Act/Collaborate/Improve) to the highest-value gaps blocking a first real design partner. Team invitations was the first of those: confirmed via a direct grep that no invite route existed at all — sign-up created exactly one user (the owner) with no way to add a second.

### Key Deliverables Built

- **Schema:** `invitations` table — `workspace_id`, `email`, `role` (reuses the existing `user_role` enum), `token_hash`, `status` (`pending | accepted | revoked` — "expired" is a read-time condition on `expires_at`, not a fourth stored state needing a background job), `invited_by_user_id`, `expires_at`, `accepted_at`. RLS + workspace-scoped indexes + a unique index on `token_hash`. Migration `0010_curious_lyja.sql`.
- **Deliberately not `users.status = 'invited'`** (declared in the schema since Phase 0, unused): `users.password_hash` is `NOT NULL`, and an invited-but-unaccepted person has no password yet. Same reasoning `conversation_notes`/`integration_action_logs` already established — when something doesn't fit an existing entity's invariants, it gets its own table rather than a nullable-hack column. `users.status = 'invited'` remains declared-but-unused.
- **Token mechanism:** mirrors `workspace_api_keys`, not the widget's JWT ticket — an opaque random token (`generateInvitationToken`, `apps/api/src/modules/users/invitation-token.ts`), only its SHA-256 hash stored, because revocability was a hard requirement here (a stateless JWT can't be revoked server-side, which is fine for a 60-second WS ticket and wrong for something with an explicit "Revoke" button).
- **`auth_resolver` extended, not a new bypass role:** two migrations (`0011`, `0012`) grant narrow, additive `SELECT` privileges — `invitations(id, workspace_id, email, role, status, expires_at, token_hash)` and `workspaces(name)` on top of the existing `(id, slug, status)` grant. Same chicken-and-egg problem `findApiKeyByHash`/`findWorkspaceBySlug` already solve: an invitation token has to resolve to a workspace before any tenant context exists.
- **`EmailSender` interface** (`apps/api/src/modules/users/email-sender.ts`), explicitly requested: v1's only implementation is `NullEmailSender` (a no-op, not a silent stub — same honesty as `UnsupportedSourceTypeError`). The invite URL is always returned directly to the caller regardless, so no email ever sending doesn't block the feature. Adding Resend later is one new file plus one line in `createEmailSender()` — nothing in the service, routes, or schema should need to change.
- **`invitation.service.ts`:** `createOrResendInvitation` (role-escalation check, rotate-if-pending-exists), `listWorkspaceInvitations`, `revokeWorkspaceInvitation`, `getInvitationPreview` (public, via `auth_resolver`), `acceptInvitation` (public, concurrency-safe).
- **Routes:** `apps/api/src/modules/users/invitation.routes.ts` mixes session-gated management routes (`POST`/`GET`/`DELETE /workspaces/invitations`) with public accept-flow routes (`GET`/`POST /invitations/:token[/accept]`) in one plugin, using per-route `preHandler` rather than a blanket hook — same shape `auth.routes.ts` already uses for signup/login vs. `/auth/me`. `user.routes.ts` adds a read-only `GET /workspaces/users` (team member list) — a near-free addition; building an invite flow with no way to see who's already on the team would be an incomplete UX.
- **`setSessionCookie` extracted** from `auth.routes.ts` into `session-token.ts` — the invitation accept flow became a second caller needing the identical cookie-setting logic, the textbook "second use" moment for a helper that had stayed local until now.
- **Dashboard:** `/team` (members list, pending invitations with Resend/Revoke, invite form with a role dropdown filtered to what the current user is allowed to grant, and a copy-link box shown after inviting/resending) and a public `/accept-invite?token=...` page (preview, name+password form, auto-login on success — mirrors sign-up's "return token+session immediately" pattern).

### Decisions Made During Implementation

- **Only an Owner can invite someone as Owner.** An Administrator inviting someone is capped at Administrator/Support Agent. New business rule, not previously encoded anywhere — deliberate, not asked as a blocking question (close to uncontestable as a security default), but flagged explicitly since it's new behavior real workspaces will come to depend on.
- **Distinct, specific error messages for an invalid/expired/revoked/already-accepted token**, not a generic "not found." A deliberate departure from the "don't reveal existence" pattern used for cross-tenant conversation lookups elsewhere — there the caller might be an unauthorized prober; here the caller already possesses the actual link, so there's no confidentiality benefit to being vague, only worse UX.
- **The accept endpoint never accepts a client-supplied email** — it's always read server-side from the invitation record. Security-critical: allowing a client-supplied email would let anyone holding a valid token for *any* address register themselves under a *different* one in that workspace.
- **Concurrency handled with a single conditional `UPDATE ... WHERE status = 'pending' AND expires_at > now()`**, not a separate read-then-write — the real guard against a double-accept race, not just an initial convenience check.

### Bugs Found and Fixed During Live Verification

- **The `auth_resolver` grant from migration `0011` omitted `token_hash`**, even though `findInvitationByTokenHash` filters on it. Postgres requires column-level `SELECT` privilege on *every* column a query references anywhere — including `WHERE` conditions — not just the columns actually returned. Every accept-flow lookup failed with "permission denied for table invitations" until this was caught by actually calling the route, not just reading the grant back. `workspace_api_keys`' existing grant already included `key_hash` for the identical reason; this one should have matched it from the start. Fixed with migration `0012`, and the code comment in `auth-resolver-client.ts` rewritten to make the distinction (granted-for-filtering vs. selected-for-return) explicit so it isn't missed again.

### Verified

- Role-escalation rule confirmed live, not just by inspection: invited a real Administrator through the full accept flow, then confirmed that Administrator's own session is still rejected (403) attempting to invite someone as Owner, while inviting as Support Agent from the same session succeeds.
- Concurrency: two simultaneous `accept` requests for the same token fired in parallel — exactly one returned 201 and created a user, the other returned a clean 404, confirmed by a direct DB count (`1` user, not `2`).
- Resend/rotation: inviting the same pending email twice produces two different tokens but exactly one pending row; the pre-rotation token stops working immediately.
- Revoke: revoking a pending invitation makes both preview and accept fail cleanly; revoking an already-revoked invitation is a clean no-op 404, not an error.
- Expiry: an invitation with `expires_at` forced into the past is correctly rejected by preview with "This invitation has expired."
- "Already a member" rejection: inviting an email that already has an active account in the workspace returns a clean 409 rather than a duplicate/confusing state.
- Tenant isolation: a Beta Co session's `GET /workspaces/invitations` and `GET /workspaces/users` both returned only Beta Co's own data; a direct `DELETE` against an Acme invitation's id from Beta Co's session returned 404.
- Browser-verified via Playwright end-to-end, including the part curl can't exercise: logged in, sent an invite from `/team`, followed the revealed link in a **separate, session-less browser context** (simulating the actual recipient), saw the correct workspace/email/role preview, accepted, and landed back on the dashboard **already logged in** as the new user. Zero console errors, zero failed requests on the full pass.
- All test invitations/users removed after verification — workspace state matches what it was before this milestone's testing began.

### Found in Pre-Commit Review (fresh read, assuming nothing about the author's own intent)

A second pass — explicitly re-reading every file fresh, looking for security issues, privilege escalation, lifecycle bugs, tenant-isolation gaps, DB/index issues, race conditions, and UX inconsistencies — caught five more issues, all fixed and re-verified live before commit:

- **Invitation email was never normalized.** No `.toLowerCase()`/`.trim()` anywhere in the invitation flow, and `users_workspace_email_unique` is a plain case-sensitive index — so `user@acme.test` and `User@Acme.test` were treated as different people by every check (pending-invite dedup, already-a-member check), letting the same real address end up with two live invitations or two accounts. Fixed by normalizing once in `createOrResendInvitation` before any DB read, and — since half-fixing this would leave `signUp`/`logIn` comparing against un-normalized data — normalized there too for consistency.
- **Invitation creation had a real TOCTOU race**, the same class of bug already found and fixed for *accepting* in the original build, just not applied to *creating*: `createOrResendInvitation` was check-then-branch-then-write, not atomic, so two concurrent requests for the same brand-new email (a double-click, or two admins inviting simultaneously) could both pass the "no existing pending invite" read and both insert. Fixed with a partial unique index, `invitations_workspace_id_email_pending_unique` on `(workspace_id, email) WHERE status = 'pending'` (migration `0013_even_sister_grimm.sql`) — confirmed at the raw DB level to actually reject the second insert, not just in the happy path.
- **A real bug surfaced *while fixing* the race above**: the friendly-error translation for the resulting unique-violation didn't fire — a genuine concurrent-create race still produced a raw 500. Root cause: Drizzle wraps the raw `pg` driver error in a `DrizzleQueryError`, and the actual `code: '23505'` lives on `.cause`, not the top-level error object. The original `isUniqueViolation` check only looked at the top level. **This same bug was found, live, in `auth.service.ts`'s pre-existing `isUniqueSlugViolation`** — meaning the slug-collision retry logic from Phase 0 had likely never actually triggered on a real collision; it silently fell through to a raw error instead of retrying. Both fixed with the same corrected check (top-level `code` OR `cause.code`).
- **`acceptInvitation` never checked `workspace.status`.** `logIn` already rejects a suspended workspace; accept didn't, so a stale invitation could be accepted into a suspended workspace and hand out a working session for up to 7 days (sessions can't be force-revoked) into a workspace that's supposed to be locked out. Fixed by mirroring `logIn`'s exact guard inside the accept transaction. Verified live by suspending a real workspace mid-test and confirming accept correctly rejects while a not-yet-suspended preview still worked as expected.
- **`/team`'s `handleResend`/`handleRevoke` had zero error handling** — no `try/catch`, no busy state, unlike `handleInvite` right above them; any failure was a silent unhandled promise rejection. Fixed to match `handleInvite`'s pattern. Also fixed the underlying UX gap that made this worse: the Resend button rendered unconditionally even for a pending invitation the current viewer isn't allowed to resend (e.g., an Administrator viewing a pending Owner-level invite) — now hidden client-side (`invitation.role !== "owner" || canInviteOwner`) in addition to staying backend-enforced, so the dead-end never gets reached in the common case, with a real error message as the fallback if it ever does.

**Item 6** (missing index for `getPendingInvitationByEmail`'s query shape) was resolved as a free side effect of the partial unique index above — a unique index on `(workspace_id, email) WHERE status = 'pending'` is exactly the index that query needed, so no separate migration was necessary.

**Item 7, accepted as a v1 limitation, not fixed:** accepting an invitation while already logged into a different session silently overwrites the existing session cookie with no warning. Low-probability (requires already being logged in when opening someone else's invite link) and not a security hole — the user ends up in exactly one workspace's context either way, matching the existing one-session-cookie design — but a real, untested edge case. Worth a warning ("you're currently logged in as X, accepting will switch you to Y") if it turns out to matter in practice; not worth the complexity pre-emptively.

## Milestone: Knowledge Sources — File Upload, PDF, Website, DOCX

**Status:** ✅ Completed & Verified

The second milestone off the roadmap review, after Team Management: expanding knowledge ingestion beyond hand-pasting text, the other highest-value gap identified for a first design partner. `knowledge_sources`' schema already anticipated `website`/`pdf`/`docx` as type-enum values since Phase 2 — this milestone needed zero schema change, just the ingestion logic the schema was always waiting for.

Built and verified incrementally, one format at a time, rather than all at once: **TXT/Markdown → PDF → Website → DOCX**, each implemented and confirmed working against a real file/URL before moving to the next.

### Key Deliverables Built

- **New dependencies:** `@fastify/multipart` (file uploads), `unpdf` (PDF text extraction, chosen over `pdf-parse` specifically to avoid a known import-time side-effect bug in that package), `mammoth` (DOCX), `cheerio` (HTML text extraction).
- **`apps/api/src/modules/knowledge/text-extraction.ts`** — plain functions (`extractPdfTextFromBuffer`, `extractDocxTextFromBuffer`), not a provider interface: unlike `AiProvider`/`IntegrationProvider` there's no vendor to swap here, just which library parses which file format. Extended one function at a time as each format was built, per explicit instruction before starting this milestone.
- **`apps/api/src/modules/knowledge/website-extraction.ts`** — `fetchAndExtractWebsiteText(url)`, native `fetch` + `cheerio`, with a basic (not exhaustive) SSRF guard rejecting `localhost`/`.local`/private-range IPv4 literals before ever fetching. Explicitly not a full SSRF defense (no DNS-resolution check for a hostname that rebinds to a private IP) — proportionate given this is a role-gated, admin-only endpoint, not public-facing.
- **Multiple manually entered URLs, not sitemap crawling** — `POST /knowledge/sources/website` accepts an array of URLs (the dashboard splits a one-per-line textarea client-side), each becoming its own `knowledge_sources` row processed independently. A business pastes their most important pages directly; full sitemap-driven bulk crawling (crawl caps, dedup, partial-failure handling across an unbounded page count) is deliberately out of scope, per explicit instruction, until real usage shows one-at-a-time is too tedious.
- **`knowledge.service.ts` additions:** `createKnowledgeSourceFromUpload` (file uploads — extraction happens synchronously, before insert, since it's fast and CPU-only; a corrupt file fails immediately with a clear error rather than silently landing in `status: 'failed'` later) and `createKnowledgeSourcesFromUrls` (website — insert happens immediately with a URL placeholder title and `content: null`; the fetch stays in the existing unawaited background step since it's a network call that can be slow or fail, exactly like Phase 2's original "don't hold the response open" reasoning, just applied to a fetch instead of an embedding call).
- **`chunkFaqContent()`** (`chunker.ts`) — the `"faq"` type has existed since Phase 2 but was never chunked any differently from plain text. Pairs consecutive blank-line-separated blocks whenever the first looks like a question (ends in `?`, or a `Q:`/`Q.` prefix) and the second doesn't, keeping question and answer in the same chunk regardless of length. Falls back to the generic `chunkText` when nothing in the content actually looks like a Q/A pair — graceful degradation, not a hard failure on non-FAQ-shaped content.
- **Dashboard (`/knowledge`):** a file picker (title + file, calling `/knowledge/sources/upload` via `FormData`) and a website textarea (one URL per line, calling `/knowledge/sources/website`), alongside the existing paste-text form. The sources list already rendered `type` generically, so it needed no changes beyond showing `sourceLocation` for website sources.
- **`apps/dashboard/lib/api.ts` fix, a real prerequisite bug**: `apiFetch` unconditionally set `Content-Type: application/json` whenever a body was present — for a `FormData` body (file upload) this silently breaks the request, since the browser needs to set its own `Content-Type` with the multipart boundary and a manual override prevents that. Fixed to skip the JSON header specifically when the body is a `FormData` instance.

### Decisions Made During Implementation

- **Text only, never the original binary.** Extracted text is the only thing stored (in the existing `content` column); the uploaded file itself is discarded after extraction. Nothing anywhere requires re-downloading the original, so this avoids standing up object storage as a prerequisite for a capability that doesn't actually need it.
- **A real page `<title>` replaces the URL placeholder once fetched**, but only if one was actually found — a fetch that succeeds without finding a `<title>` tag keeps the URL as the display title rather than overwriting it with nothing.
- **`unpdf` over `pdf-parse`** — not just a style preference. `pdf-parse` has a known import-time side effect (it attempts to read a bundled test fixture off disk on module load in some environments) that's a real reliability landmine for a production dependency; `unpdf` (built on Mozilla's pdf.js) doesn't have this problem and is designed for exactly this kind of server-side use.
- **File size capped at 15MB** (`@fastify/multipart`'s `limits.fileSize`) and URL batches capped at 20 per submission — both defensive bounds even though neither is a paid-per-call external API, matching the existing "don't send an unbounded batch" principle applied to resource consumption generally, not just billing.

Zero console errors, zero failed requests.

### Found in Pre-Commit Review (production-incident focus, not style)

A dedicated pass explicitly scoped to security/performance/production-incident classes of bug (SSRF, upload validation, memory/blocking, duplicate content, embedding pipeline edge cases, tenant isolation, rate limiting, indexing, cleanup) rather than style — three real issues found and fixed, one suspected issue investigated and confirmed already handled correctly.

- **Unbounded concurrent processing across a URL batch.** `createKnowledgeSourcesFromUrls` fired all N background jobs at once (`for (const source of sources) { void processKnowledgeSource(...) }`) — up to `MAX_URLS_PER_SUBMISSION` (20) concurrent outbound fetches and concurrent calls to Voyage's paid embedding API from a single submission, directly contradicting Phase 2's own established "batch sequentially, not in parallel" rule for exactly this class of external call, just reintroduced at the source level instead of the chunk level. Fixed with `processSourcesSequentially` — a plain `for...of` loop with `await` inside, no concurrency-limiter library, per explicit instruction to keep this minimal. Verified live: submitting 3 URLs at once produced staggered completion timestamps (~700ms-1s apart) rather than near-simultaneous ones, consistent with genuine sequential execution.
- **No timeout on synchronous PDF/DOCX extraction.** Extraction runs inline in the upload request path with no worker-thread isolation (deliberately, to fail fast on a corrupt file) — a pathological file (DOCX is a zip archive; a "zip bomb" is a well-known, trivial-to-construct attack) had no upper bound and could hang the single Node process handling every workspace's requests, not just the uploader's. Fixed with a `Promise.race`-based timeout (20s, within the requested 15-30s range) in `text-extraction.ts`, wrapping both `extractPdfTextFromBuffer` and `extractDocxTextFromBuffer`. Documented honestly in the code comment: this mitigates the common case (a slow-but-eventually-resolving extraction) but can't preempt a genuinely synchronous, non-yielding CPU loop already blocking the event loop — full protection needs worker-thread isolation, explicitly deferred for v1 per instruction. Verified two ways: a real PDF still extracts correctly with the wrapper in place (no regression), and the race logic itself was tested in isolation against a promise that never resolves, confirming it rejects at the configured time, not early or late.
- **No duplicate-content detection for website ingestion.** Nothing checked for an existing source with the same URL before inserting — and this milestone's whole point (convenient bulk-add) makes accidental duplication a realistic, common case, unlike the deliberate one-at-a-time paste flow. Fixed with `getKnowledgeSourceBySourceLocation`, checked per-URL inside the same loop that now processes sequentially anyway; a duplicate is skipped with a friendly message rather than silently creating a redundant, separately-embedded source. `POST /knowledge/sources/website` now returns `{ sources, skipped }`; the dashboard surfaces the skipped list inline ("Already in your knowledge base, skipped: ..."). Deliberately an application-level check, not a DB-level unique constraint — the realistic risk here is the same admin resubmitting overlapping URL lists across separate sessions, not truly concurrent requests racing each other, so the added complexity of a partial unique index (as was needed for the invitation-email race, a genuinely concurrent, higher-frequency scenario) wasn't judged worth it here. Verified live: resubmitting an already-ingested URL alongside a new one correctly skipped only the duplicate, added only the new one, and left exactly one row in the database for the repeated URL.
- **Investigated and confirmed *not* a bug**, worth recording so it isn't re-investigated later: whether the 15MB upload-size limit could be silently bypassed via truncation instead of rejection. Read `@fastify/multipart`'s source directly rather than assuming — its default `throwFileSizeLimit: true` behavior (which this registration doesn't override) makes `toBuffer()` throw a proper `FST_REQ_FILE_TOO_LARGE` error rather than returning a truncated buffer. Verified empirically too: a 20MB upload against the 15MB limit returned a clean `413`, with no orphaned `knowledge_sources` row left behind.

### Verified (post-fix)

- Duplicate detection: resubmitted `https://example.com/` alongside a new URL — response correctly reported it in `skipped`, only the new URL was added, and a direct DB count confirmed exactly one row exists for the repeated URL.
- Sequential processing: a 3-URL batch showed staggered `updated_at` timestamps on completion, not simultaneous ones — consistent with the code's actual `for...of`/`await` shape, not `Promise.all`.
- Extraction timeout: a real PDF upload still extracts and completes correctly with the timeout wrapper in place (no regression to the happy path); the timeout race logic itself, tested in isolation against a promise that never resolves, rejected at the configured time.
- Full typecheck clean across all packages after all three fixes.

### Fourth issue, found on a direct follow-up question rather than a fresh review pass

Asked directly afterward whether any High/Medium-severity issues remained that would block a design-partner pilot. One genuine gap had been missed in the review above: `fetchAndExtractWebsiteText` called `response.text()` unconditionally, with no limit on how much it would buffer into memory. The file-upload path has a hard 15MB cap (`@fastify/multipart`'s `limits.fileSize`) specifically to bound memory; the website path never got the equivalent treatment. The 15-second fetch timeout bounds *time*, not *size* — a fast connection can transfer a large amount of data well within 15 seconds, so it provided no real protection here.

- **Fixed with a streaming, size-limited read (`readBodyWithSizeLimit` in `website-extraction.ts`)**, not a buffer-then-check: a declared `Content-Length` header exceeding the limit is rejected before any body bytes are read; independently (since `Content-Length` can be missing, chunked, or simply wrong), the body is read via `response.body.getReader()` with a running byte count, calling `reader.cancel()` and throwing the moment the running total crosses the limit — never continuing to download data that's just going to be discarded, and never holding the full oversized body in memory even transiently.
- **Limit: 15MB, deliberately matching the existing upload limit** rather than a separately-tuned value — one uniform "nothing this system ingests exceeds 15MB" rule is simpler to reason about than two independently-justified numbers, and it doesn't meaningfully under-protect: real HTML pages are virtually always well under 1-2MB, so a response actually reaching double-digit megabytes of raw HTML is already abnormal regardless of the exact threshold chosen. Kept as its own constant in `website-extraction.ts` rather than importing `knowledge.routes.ts`'s, since that would run the module dependency the wrong way (routes depends on this module, not the reverse) — the two are cross-referenced by comment instead of a shared import.
- **Error**: a dedicated `ResponseTooLargeError` with the exact message "Website content exceeds the maximum supported size." — not routed through the existing `WebsiteFetchFailedError`, whose constructor prepends "Could not fetch this page: ", which would have altered the required wording.
- **No partial state on rejection**: unchanged from the existing control flow, not a new mechanism — `fetchAndExtractWebsiteText` throwing before `updateKnowledgeSourceContent` is ever called means the source keeps `content: null` and no chunks are ever inserted; `processKnowledgeSource`'s existing outer catch marks the source `status: 'failed'` with the error message, the same path every other extraction failure already takes.

**Verified**: the streaming logic was tested in isolation (temporarily exporting the two new pieces, then reverting) against real, in-process `Response`/`ReadableStream` objects — not a reimplementation. A small body decoded correctly (no regression). A stream offering 30MB across 30 one-megabyte chunks was cut off after exactly 16MB (the limit crossed mid-chunk), threw `ResponseTooLargeError` with the exact required message, and `reader.cancel()` was confirmed called — proving the implementation genuinely aborts mid-stream rather than buffering the full body first. Separately, a full live regression pass through the real API confirmed normal website ingestion (`example.com`) is unaffected: fetch, extraction, chunking, embedding, and search all still complete correctly end to end.

**Status:** ✅ Completed & Verified

The top item on every prior phase's "recommended next" list, finally picked up: this codebase had zero automated tests before this milestone, despite seven phases/milestones of business logic and the one bug class ("a workspace sees another workspace's data") that's genuinely unacceptable. Preceded by an extended design review (multiple passes, each one deliberately re-challenged rather than accepted on the first pass) before any test code was written — the review is what produced the actual architecture below, not an afterthought bolted onto a naive first draft.

### Key Deliverables Built

- **Test runner: Vitest**, one config per package (`packages/db/vitest.config.ts`, `apps/api/vitest.config.ts`), both pointing at a shared root `vitest.setup.ts` (loads `.env.test`, `override: true`) plus a small package-local `vitest.setup.ts` each (closes the real `pg.Pool` at teardown — `@csa/db` doesn't resolve as an importable package name from inside its own test run the way it does for a real consumer like `apps/api`, so this one piece couldn't be shared verbatim).

Isolation between tests is `TRUNCATE ... RESTART IDENTITY CASCADE` in `afterEach`, not per-test transactions — deliberately simpler than pinning a single connection across nested transactions, with `fileParallelism: false` in both vitest configs so concurrent test files can't race each other's truncates against the shared database. Documented as a trade-off to revisit only if suite runtime becomes an actual measured problem, not preemptively.

- **Real dependency injection for all three provider types**, no test-only exports anywhere:

  - `integration.service.ts`: `connectHubspot` and `lookupContact` each gained a defaulted provider-factory parameter — typed concretely as `HubSpotIntegrationProvider` for `connectHubspot` (already HubSpot-specific — `verifyConnection` was already deliberately excluded from the neutral interface) and as the neutral `IntegrationProvider` for `lookupContact` (which only ever calls the interface's own `lookupContact` method).
  - `support-orchestrator.ts`: a new `OrchestratorDeps` interface (`jobRunner`, `aiProvider`, `embeddingProvider`, `integrationProviderFactory`, all optional) as a **second, separate parameter** on the four Orchestrator functions that touch a provider (`handleCustomerMessage`, `suggestReplyForAgent`, `summarizeConversationForAgent`, `lookupContact`) — never merged into each function's existing plain-business-data params, so no route call site needed to change and production behavior is byte-for-byte identical. This is what makes `generateAiReply`'s fire-and-forget path (unexported, unreachable by any parameter threaded through `handleCustomerMessage`'s own business-data DTO) deterministically testable: swap in `SynchronousJobRunner` plus a fake provider via `deps`, and `handleCustomerMessage`'s returned promise doesn't resolve until that path has genuinely finished — no polling, no hub-subscription trick, no `__set...ForTesting` export.
- **`apps/api/src/test-support/`**: `reset-database.ts` (schema-driven `TRUNCATE`, iterates every exported Drizzle table via `is(value, PgTable)` rather than a hand-maintained name list), `fixtures.ts` (`createWorkspace`/`createUser`/`createCustomer`/`createConversation`, all built on the real repository functions, not hand-written SQL), `fake-ai-provider.ts` / `fake-embedding-provider.ts` / `fake-integration-provider.ts`. `FakeAiProvider`/`FakeIntegrationProvider` throw a loud, descriptive error if used without being configured (`.mockReply(...)`/`.mockFound(...)` etc. first) rather than silently returning a plausible-looking default — deliberate, because `generateAiReply`'s errors are swallowed (`.catch(() => {})`), so a misconfigured fake would otherwise look identical to "the AI correctly declined to answer."
- **`packages/db/src/tenant-isolation.test.ts`**: the generic, schema-driven foundation-level guarantee. Iterates every exported table with a `workspace_id` column and requires a one-entry `fixtures` map registration for each; a new tenant table added later without a registered fixture fails the suite loudly ("No fixture registered for...") instead of silently shipping with zero isolation coverage — directly targeting the exact failure mode (a table missing RLS/an index, twice already caught only by manual review) this codebase's own history shows is genuinely easy to miss. `workspaces` itself gets one direct, hand-written check outside the loop (structurally different policy — no `workspace_id` column, isolated via its own `id` against `app.workspace_id` instead, with an intentionally open `INSERT` policy since no context exists yet at creation time).
- **`apps/api/src/orchestrator/support-orchestrator.test.ts`**: all nine exported Orchestrator functions, plus two hand-written two-workspace cross-tenant checks (`handleCustomerMessage`, `claimConversation` each correctly 404 against a different workspace's conversation id) — paired with the generic suite above rather than duplicating it, per the earlier design review's conclusion that the generic table-driven suite is the right home for exhaustive per-table coverage and a small number of scenario-based checks is the right home for real business-logic-bearing flows.

### Decisions Made During Implementation

- **Fake at the lowest layer (the raw provider interface), never at the service-function layer.** A test that injects a fake `AiProvider` still executes all of `ai.service.ts`'s and the Orchestrator's real logic (the grounding-floor filter, the confidence-escalation threshold, prompt construction) — only the actual network call is replaced. Injecting a fake `generateSupportReply` instead would bypass that real logic entirely, and — as `ai.service.ts` inevitably grows real cross-cutting concerns (retries, telemetry, per-workspace provider resolution) over the life of this codebase — would silently stop exercising whatever gets added there. Deliberately re-litigated (not just assumed) during design: is this a permanent principle or an artifact of `ai.service.ts` currently being a thin pass-through? Conclusion: the seam tracks the actual external I/O boundary (the vendor HTTP call), not which of *our own* files happens to own a decision, so it's robust to business logic moving between the Orchestrator and the service layer — it would only need to move if the provider call itself stopped being inert data-in/data-out (a genuinely agentic redesign where a model's own execution directly causes side effects), which is a different system, not a refactor.
- **No `__set...ForTesting` exports anywhere**, by explicit design constraint, not just preference. The one seam that couldn't be reached by an ordinary defaulted parameter — `generateAiReply`'s and `processKnowledgeSource`'s fire-and-forget internal use of a provider — is solved by `JobRunner` making the call directly awaitable in tests, at which point an ordinary parameter (`deps`) reaches it after all. A full closures-over-injected-dependencies rewrite of the Orchestrator (a real "composition root" pattern) was considered and rejected as disproportionate — it would abandon the Orchestrator's deliberate plain-function shape for a benefit the much smaller `deps`-as-second-parameter pattern already delivers.
- **`OrchestratorDeps` is a second, separate parameter, never merged into a function's existing business-data params.** Keeps every DTO's shape exactly what a route handler naturally has to supply; a caller that doesn't care about overriding anything (every real route today) doesn't pass it at all and pays zero cost.
- **The generic RLS suite lives in `packages/db`, not `apps/api`**, even though the actual repository functions that query these tables live in `apps/api/modules/*`. RLS is `packages/db`'s guarantee (the schema + policies are defined there), so the suite exercises the schema tables directly via `withWorkspaceContext`, independent of whatever repository code `apps/api` happens to have today.
- **`TRUNCATE` between tests, not per-test transactions with a pinned connection.** The latter would be materially faster and give perfect isolation, but requires forcing `withWorkspaceContext`'s internal `db.transaction()` and a test's own outer transaction onto the same pooled connection — a real change to how connections get acquired. Not justified at today's suite size (39 tests, single-digit-seconds runtime); revisit only if that becomes a real, measured complaint.

## Milestone: Rate Limiting (Auth, Knowledge Ingestion, Invitations, WS Messages)

**Status:** ✅ Completed & Verified

Every phase's "known limitations" section had repeated the same line since Phase 1: "no rate limiting exists anywhere yet (login, signup, WebSocket messages, ingestion)." Picked up as the first milestone after the automated-testing foundation landed — chosen specifically because two real capabilities now trigger metered third-party API calls (Voyage embeddings on ingestion, Gemini/Anthropic on every AI reply) with zero protection against a bug, a scraper, or abuse running either up unbounded. Also the first real use of Redis: `REDIS_URL` has been provisioned since Phase 0, reserved for "the real-time hub once it runs across more than one API instance," and had connected to nothing until now.

### Key Deliverables Built

- **`apps/api/src/redis-client.ts`**: a single shared `ioredis` client, constructed from the already-provisioned `env.REDIS_URL`.
- **`apps/api/src/rate-limit.ts`**: `RateLimitExceededError` (429, extends `AppError`), `checkRateLimit(redis, key, max, windowSeconds)` — a plain fixed-window `INCR`/`EXPIRE` counter — and `rateLimitByWorkspace(redis, action, max, windowSeconds)`, a preHandler factory keyed on `request.workspaceId`. Written as small, explicit functions rather than routed entirely through `@fastify/rate-limit`'s per-route `hook` timing option, since the keys these need (`workspaceId`, `conversationId`) aren't known until after an auth preHandler has already run.
- **`@fastify/rate-limit`, backed by the shared Redis client**, registered globally in `app.ts` (IP-keyed, generous default: 300/min) as the floor every route gets for free, with tighter per-route overrides where it matters:
  - `POST /auth/signup`, `POST /auth/login` — 10 per 10 minutes, IP-keyed (the plugin's default; no workspace exists yet at signup, and login only identifies one by slug inside the body).
  - `POST /knowledge/sources`, `/knowledge/sources/upload`, `/knowledge/sources/website` — 30 per hour, **workspace**-keyed via `rateLimitByWorkspace` (every one of these routes triggers at least one real embedding-API call).
  - `POST /workspaces/invitations` — 20 per hour, workspace-keyed (invite-spam protection, and future email-deliverability/cost protection once a real `EmailSender` lands).
  - The WS `message:send` path (`widget-ws.routes.ts`) — 20 per minute, keyed by **conversationId**, checked inline via `checkRateLimit` directly (not `@fastify/rate-limit`, which only hooks into the HTTP request lifecycle and can't reach a WebSocket message). This is the actual AI-generation cost trigger in the whole codebase — the highest-priority surface of the four.

### Decisions Made During Implementation

- **Workspace-keyed, not IP-keyed, for ingestion and invitations.** The thing being protected is a workspace's own cost/spam exposure, not a single client's request volume — an office sharing one IP shouldn't have its limit oddly multiplied or divided. The WS message path is keyed even narrower, by `conversationId`, since the realistic risk there is one runaway or malicious script in a single chat, not a workspace's aggregate volume.
- **A custom `errorResponseBuilder`, not a broader `error-handler.ts`.** `@fastify/rate-limit`'s own default throws a plain `Error` carrying only `.statusCode` (no `.code`) — and `error-handler.ts`'s Fastify-error branch deliberately only trusts errors with an `FST_`-prefixed code, a narrowing already put in place during Phase 4 specifically *because* a broader "any object with a numeric 4xx `statusCode`" check had once nearly let a third-party SDK's unrelated `statusCode` field leak through. Rather than reopening that branch, the plugin is configured with `errorResponseBuilder: () => new RateLimitExceededError()`, so a rate-limit rejection becomes a real `AppError` instance and is handled by the already-correct, unmodified `AppError` branch. One consistent error type and message ("Too many requests. Please try again shortly.") across both the plugin-driven and the hand-rolled limiters.
- **`ioredis`'s named `{ Redis }` export, not the default export.** `import Redis from "ioredis"` failed to typecheck under this project's `moduleResolution: NodeNext` ("This expression is not constructable") — a known interop quirk with that package's CJS/ESM dual shape. `import { Redis } from "ioredis"` resolves to the same class without the ambiguity.

### Bugs Found and Fixed During Live Verification

- **The exact `error-handler.ts` gap described above was caught live, not by inspection.** A real curl loop against `/auth/login` correctly got `401` for the first 10 attempts, then a `500` (not the expected `429`) starting at request 11. The server log showed `@fastify/rate-limit` had correctly detected and thrown its rate-limit error with `statusCode: 429` — but `error-handler.ts` didn't recognize it as trustworthy (no `FST_`-prefixed `code`) and collapsed it to a generic 500, silently discarding the real status. Fixed with the `errorResponseBuilder` override described above; re-verified with the same curl loop, now correctly returning `429` with `x-ratelimit-limit`/`x-ratelimit-remaining`/`retry-after` headers and the intended error body.

### Verified

- **Auth**: a real 12-request curl loop against `/auth/login` — 10 requests got a normal `401` (bad credentials), requests 11–12 got a real `429` with the correct headers (`x-ratelimit-limit: 10`, `x-ratelimit-remaining: 0`, `retry-after`) and error body. An unrelated endpoint (`/health`) was hit immediately afterward and confirmed completely unaffected.
- **The hand-rolled `checkRateLimit` primitive**: exercised directly against the real Redis client (not a reimplementation) — 3 allowed calls, a 4th correctly threw `RateLimitExceededError` with `statusCode: 429`, and the key's TTL matched the configured window.
- **Workspace-keyed wiring end-to-end**: signed up a real test workspace, hit `POST /knowledge/sources` once with a real session cookie, then read the Redis key directly (`GET rl:knowledge-ingest:<workspaceId>`) and confirmed it held `1` with a TTL of ~3600s — proving `requireSession` → `request.workspaceId` → `rateLimitByWorkspace`'s key construction is wired correctly, without needing to drive a live embedding call 30 times to reach the threshold.
- Full regression: both existing test suites (`packages/db` 12/12, `apps/api` 27/27) re-run clean after every change in this milestone, plus `pnpm -r run typecheck` clean across all six packages.
- All test data (the verification workspace and its cascaded rows, the scratch Redis keys) removed after verification — confirmed via a direct `DELETE FROM workspaces` and `redis-cli DEL`, not left behind.

## Milestone: WebSocket Reconnect + Backoff (Widget & Agent Console)

**Status:** ✅ Completed & Verified

Picked as the next milestone after rate limiting on the basis of a fresh codebase review, not a features list: direct inspection of both WebSocket clients (`apps/widget/src/ws-client.ts`'s `ChatConnection`, `apps/dashboard/lib/agent-console-ws-client.ts`'s `AgentConsoleConnection`) confirmed that neither registered a `close`/`error` listener *after* the initial connection succeeded — a dropped connection (API restart, deploy, network blip) left a live customer chat or an agent's live conversation view silently dead, with zero indication, until a manual page reload. This was the only remaining gap that broke the product's core, already-shipped, real-time promise rather than a missing capability or an unfelt scale concern.

### Key Deliverables Built

- **Independent implementations in both clients**, not shared code — matching `agent-console-ws-client.ts`'s own pre-existing comment on why the two are deliberately separate (different auth: session cookie vs. API-key ticket; different subscription model: watch an existing conversation vs. initiate a new one).
- **Backoff schedule (identical in both, each its own small copy):** 1s → 2s → 4s → 8s → 16s → 30s (capped), ±20% jitter to avoid a reconnect thundering-herd if many clients drop at once (e.g. an API restart). Retries indefinitely at the 30s steady state — no "give up, please refresh" dead end.
- **`ChatConnection` (widget):** a post-open `close` listener schedules a reconnect (full two-step handshake re-run — `POST /widget/session` for a fresh ticket, since the old one is short-lived/single-use, not a raw WS URL reopen). On successful reconnect, re-sends `conversation:initiate` with the ids already persisted in `storage.ts`'s `localStorage`, resuming history exactly as a manual page reload already did. Emits two new synthesized event types, `connection:reconnecting` / `connection:restored`, through the existing `onEvent` mechanism — no second callback channel.
- **`AgentConsoleConnection` (dashboard):** same backoff and event pair. Reconnect just reopens `/agent-console/ws` (the session cookie rides along automatically, no ticket dance). Now tracks the last-`watch()`-ed `conversationId` internally so a reconnect can automatically re-send `conversation:watch` without requiring the page to re-drive it — keeps reconnection entirely self-contained inside the client.
- **UI wiring reuses the existing `connected` boolean** in both `Widget.tsx`/`ChatPanel.tsx` and the dashboard's conversation detail page — already gated the "Connecting..." status text and input-disabled state, just never updated after the first connect. Added one small `reconnecting` boolean purely to distinguish the status text ("Reconnecting..." vs. "Connecting...") since silently reusing the same first-connect copy mid-conversation could look like a full reset rather than a live recovery.
- **Explicitly out of scope, by instruction:** no message queuing for anything sent while disconnected (the send control just reflects the disabled/reconnecting state), and no shared reconnect abstraction between the two clients.

### Decisions Made During Implementation

- **A `hasOpenedOnce` guard, added after finding a real bug in the first draft (see below), not part of the original plan.** Browsers fire `close` immediately after `error` even for a connection attempt that never successfully opened — without this guard, the very first connection attempt's own failure would silently start a background reconnect loop that `connect()`'s caller (which already has its own reject/catch for that exact case) has no idea is running. Reconnection now only ever triggers for a close that follows at least one successful open.
- **`scheduleReconnect()`'s existing `if (this.reconnectTimer) return` guard is what makes a redundant double-trigger harmless**, rather than adding explicit de-duplication: a failed reconnect attempt can have both its promise rejection *and* its socket's own `close` event separately call `scheduleReconnect()`; the guard means whichever fires first wins and the second is a no-op, with no need to reason precisely about browser WS event ordering.

### Bugs Found and Fixed During Live Verification

- **The exact reconnect-loop risk described above was designed around proactively, not caught reactively** — flagged while writing the first draft, before running anything, by tracing through what happens on a first-connect failure. Fixed with the `hasOpenedOnce` flag before any live test ran.
- **A test-harness timing issue, not a product bug, cost two verification runs on the dashboard side.** The first two attempts to verify the agent console's reconnect gave it only 10s/20s to detect a killed API process before concluding it had failed; instrumenting the browser's own `WebSocket` constructor (a `Proxy` logging every open/close/error) showed the *entire* mechanism working correctly — `close` detected (code 1006), backoff retries correctly failing with `ERR_CONNECTION_REFUSED` while the server was down, and a clean recovery once it came back — just slower to detect the abrupt process kill on that particular run than the test's timeout allowed for (Windows TCP close-detection timing is not perfectly consistent across `taskkill /F` runs). Not a code fix — a reminder that a live-verification timeout needs slack for real OS/network timing variance, not just the application's own backoff math.

## Milestone: Improve — Analytics (Read-Only Dashboard)

**Status:** ✅ Completed & Verified

The first slice of the sixth and last Blueprint pillar, Improve, which had no implementation at all before this milestone. Scoped deliberately narrow after a review of `docs/00`/`02`/`04`: unlike every other pillar, `04_Domain_Model.md` names an "Analytics" entity but never commits to a schema for it - a genuinely open design space, not a follow-the-precedent situation. Rather than guess at a schema for Customer Satisfaction or "business recommendations" (the vaguest, least-defined item in the pillar), this milestone scoped to exactly what's free: read-only aggregation over data every prior phase already writes (`conversations.status`/`metadata`, `messages.metadata` on AI replies, knowledge-chunk citations) - zero schema changes, zero new capture surfaces.

### Key Deliverables Built

- **`apps/api/src/modules/analytics/`** - `analytics.repository.ts` (five aggregate queries: conversation volume by day, status breakdown, escalation-reason breakdown, AI stats, top-cited knowledge sources), `analytics.service.ts` (wraps `withWorkspaceContext`, assembles the `AnalyticsOverview` DTO and derives `resolutionRate`/`escalationRate`), `analytics.routes.ts` (`GET /analytics/overview?days=1-180`, session + `owner`/`administrator`-gated - business-insight data, same tier as API keys/integrations rather than open to every role).
- **Escalation-reason breakdown reads `conversations.metadata.escalation.reason`, not current status.** That field is merged in once by `escalateConversation` and never cleared (Phase 3), so it survives a conversation later moving to resolved/closed - counting on it is what makes the escalation-rate metric "ever escalated," not "currently escalated" (which would silently undercount every escalation a human has since resolved).
- **Top-cited knowledge sources via one raw `scopedDb.execute()` query** - `jsonb_array_elements` over `messages.metadata->'citations'` has no equivalent in Drizzle's fluent builder, so this is the one genuinely raw SQL query in the module (the same escape hatch `tenant-context.ts` uses for `set_config`), but every table/column reference still goes through real Drizzle schema objects rather than hand-written snake_case, so a future column rename doesn't leave a silently-broken string behind.
- **`apps/dashboard/app/analytics/page.tsx`** - stat tiles (conversations, resolution rate, escalation rate, avg. AI confidence), plain CSS width-percentage bar lists for volume/status/escalation-reason breakdowns (no charting dependency - the first chart-shaped page in the dashboard, and a handful of horizontal bars didn't justify one), an AI-performance section (token totals, provider/model split), a most-cited-sources list, and a 7/30/90-day range toggle. Nav link added to the dashboard home.

### Decisions Made During Implementation

- **Role-gated to `owner`/`administrator`, not open to `support_agent`** - a deliberate call, not asked as a blocking question: workspace-wide business metrics are a different category from queue-handling work, matching the precedent API-key and integration management already set (both owner/admin-only even for reads).
- **Sequential queries inside `withWorkspaceContext`, not `Promise.all`** - the first draft used `Promise.all` across the five repository calls; a live test run surfaced a real node-postgres deprecation warning ("Calling client.query() when the client is already executing a query is deprecated") because every query shares the one pg client `withWorkspaceContext`'s transaction holds - concurrent queries on a single client don't actually run concurrently, they just queue while logging a warning today and are slated to become a hard error in pg@9. Fixed to plain sequential `await`s before this was ever committed.
- **`days` range parameter (default 30, 1-180) rather than a fixed window** - cheap to support via one Zod-validated query param, and lets the same endpoint serve the dashboard's 7/30/90-day toggle without three separate routes.

## Milestone: Improve — Customer Satisfaction (CSAT)

**Status:** ✅ Completed & Verified

The second Improve slice, and the one genuinely new capture surface the pillar needed - the read-only Analytics milestone deliberately deferred CSAT specifically because it required a new schema decision, unlike everything else in that milestone. Scoped to the smallest sensible rating UX per explicit instruction: a binary thumbs-up/thumbs-down rather than a star scale, upsertable rather than one-shot.

### Key Deliverables Built

- **Schema:** `conversation_ratings` (`workspace_id`, `conversation_id`, `rating` enum `up`/`down`, timestamps) - RLS-enabled, a `(workspace_id, created_at)` composite index matching `knowledge_sources`' identical query shape, and a unique index on `conversation_id` (not a composite key) - one rating per conversation, by design, not one row per submission. Migration `0014_careful_energizer.sql`, inspected before applying; `app_user`'s default-privileges grant covered it automatically, confirmed directly (`\dp conversation_ratings`) rather than assumed.
- **`apps/api/src/modules/conversations/conversation-rating.repository.ts`:** `upsertConversationRating`, a single `INSERT ... ON CONFLICT (conversation_id) DO UPDATE`, mirroring `integration.repository.ts`'s `upsertIntegration` pattern exactly.
- **Orchestrator addition:** `rateConversation(workspaceId, conversationId, rating)` - the conversation is looked up and ownership-checked before the upsert, per the Orchestrator's standing "never trust a client-supplied id at face value" rule. Single-module (no cross-module coordination, unlike most Orchestrator functions), but placed there anyway to match the established precedent that every *widget-facing* write goes through the Orchestrator (`initiateConversation`/`handleCustomerMessage`), not just cross-module ones.
- **Route:** `PATCH /widget/conversations/:id/rating`, API-key authenticated like `widget-ws.routes.ts`'s `POST /widget/session` - a plain REST call, not a WebSocket message, since a rating isn't a live event anything else needs to react to. The `/widget` URL prefix is load-bearing, not cosmetic: `app.ts`'s CORS delegator branches on it for open-origin, no-credentials CORS (the widget runs on arbitrary third-party sites) instead of the dashboard's locked-to-`DASHBOARD_ORIGIN` policy - confirmed live, not just by inspection (see Verified).
- **Widget UI:** a "Rate this chat: 👍 👎" row in `ChatPanel.tsx`, shown once a conversation exists, replaced by "Thanks for your feedback!" after a confirmed (not optimistic) successful submit. `ChatConnection.rateConversation()` (`ws-client.ts`) is a plain `fetch`, the same shape `startHandshake()` already uses for the ticket exchange - no WS protocol change needed.
- **Analytics extension:** `analytics.repository.ts` gained `getCsatBreakdown`; `AnalyticsOverview` gained `totalRatings`, `csatScore` (positive-rating rate, denominated on ratings submitted, not total conversations - most conversations never get rated, so scoring against `totalConversations` would silently understate an otherwise-healthy workspace), and `csatBreakdown`. Dashboard `/analytics` gained a "Customer satisfaction" stat tile and breakdown section, same `BarList`/empty-state pattern as escalation reasons.

### Decisions Made During Implementation

- **Upsert, not insert-only.** A customer changing their mind (or re-rating after a page reload) updates the same row rather than erroring or creating a duplicate - the unique index on `conversation_id` is what makes this both correct and race-safe, not just an application-level check.
- **Confirmed, not optimistic, UI state.** The widget's rating buttons only flip to the "Thanks for your feedback!" state once the PATCH actually succeeds - no retry/error UI for a first pass; a failed submit just leaves the buttons as they were and the customer can tap again.
- **A resumed conversation always starts looking unrated, even if a rating already exists** - `initiateConversation`'s response doesn't carry the existing rating, and extending it to do so was judged out of scope (touching Phase 1's core resume DTO for a cosmetic gap, not a correctness one). Explicitly documented as a v1 limitation in `Widget.tsx` rather than silently accepted: harmless, since re-rating is a safe upsert, not a duplicate.
- **CSAT score denominated on ratings submitted, not total conversations** - a workspace where 2 of 200 conversations got rated, both positively, should show 100%, not 1%. The dashboard's stat tile makes this legible by pairing the score with its own "N ratings" context rather than conflating it with conversation volume.
- **No role gating on the rating endpoint itself** - unlike every dashboard-facing route, this one is customer-facing (API-key authenticated), so there's no `WorkspaceRole` to check; the only access control that applies is "does this conversation belong to this workspace's API key," which `rateConversation`'s ownership lookup already enforces.
